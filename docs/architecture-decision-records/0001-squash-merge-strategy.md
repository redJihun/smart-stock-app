# ADR-0001: Squash Merge + 패턴C 커밋 메시지 전략 채택

| 항목 | 내용 |
|------|------|
| 상태 | Accepted |
| 날짜 | 2026-03-13 |
| 결정자 | 홍지훈 |

---

## 맥락 (Context)

브랜치 작업 완료 후 일반 merge(fast-forward)로 main에 병합하면
브랜치 내 세부 커밋이 모두 main 이력에 그대로 쌓여 히스토리가 길고 노이즈가 많아지는 문제가 있다.

이슈 트래커를 사용하지 않는 소규모 개인 프로젝트이므로,
커밋 메시지 자체가 변경 맥락을 보존하는 유일한 수단이다.
브랜치를 삭제하면 세부 커밋 이력도 함께 사라지기 때문에,
병합 커밋 메시지에 변경 내역을 충분히 담는 것이 중요하다.

병렬 프로젝트인 issuance-fastapi에서 동일한 전략(ADR-0001)을 채택하여 운용 중이며,
일관성을 위해 이 프로젝트에도 동일 전략을 적용한다.

## 결정 (Decision)

브랜치를 main에 병합할 때 **Squash Merge를 기본 전략으로 채택**한다.

커밋 메시지는 **패턴C (Why + Changes 목록 혼합)** 형식으로 작성한다.

```
<type>(<scope>): <한 줄 요약>

<변경 이유 — 왜 이 작업이 필요했는지>

Changes:
- 세부 변경 항목 1
- 세부 변경 항목 2
```

### 브랜치 유형별 병합 방식

| 브랜치 유형 | 병합 방식 | 비고 |
|------------|----------|------|
| `feat/`, `chore/`, `docs/`, `refac/` | Squash merge | 기본 |
| `fix/` (단일 커밋) | Fast-forward merge | 핫픽스 1건 |
| `fix/` (다중 커밋) | Squash merge | |

### 커밋 타입 목록

| 타입 | 설명 |
|------|------|
| `Feat` | 새로운 기능 추가 |
| `Fix` | 버그 수정 |
| `Docs` | 문서 수정 |
| `Style` | 코드 포맷팅 |
| `Refac` | 코드 리팩토링 |
| `Test` | 테스트 코드 추가 |
| `Chore` | 빌드, 패키지, 설정 파일 수정 |

## 결과 (Consequences)

### 이점 (Benefits)

- `git log --oneline`이 브랜치 단위의 의미 있는 커밋으로만 구성되어 가독성이 높아진다
- 브랜치 내 WIP/수정 커밋이 main 이력에 노출되지 않는다
- 이슈 트래커 없이도 커밋 메시지 본문만으로 변경 맥락을 추적할 수 있다

### 단점 (Drawbacks)

- 브랜치 내 세부 커밋을 main에서 직접 `git blame`으로 추적할 수 없다
- 병합 시 커밋 메시지를 신경 써서 작성해야 하는 추가 작업이 생긴다

### 리스크 (Risks)

- 브랜치를 삭제하기 전에 병합 커밋 메시지가 충분히 작성되지 않으면 맥락이 소실된다
