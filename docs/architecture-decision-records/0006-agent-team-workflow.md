# ADR-0006: 에이전트 팀 워크플로우 채택 (멀티 터미널 + 서브에이전트)

| 항목 | 내용 |
|------|------|
| 상태 | Accepted |
| 날짜 | 2026-03-13 |
| 결정자 | @hong |

---

## 맥락 (Context)

Claude Code는 단일 세션으로 작업할 경우 컨텍스트 창이 점차 소진되며,
복잡한 기능 구현 시 탐색·구현·검증이 같은 컨텍스트에 섞여 효율이 낮아진다.

또한 모든 단계에 동일한 고비용 모델(Sonnet/Opus)을 사용하면
설계가 이미 결정된 반복적 작업(보일러플레이트, 테스트 작성, 린트 수정 등)에도
불필요하게 높은 비용이 발생한다.

해결해야 할 문제:
- **컨텍스트 소진**: 긴 작업 세션에서 초기 설계 맥락이 밀려남
- **비용 비효율**: 단순 구현 작업에도 고비용 모델 사용
- **병렬 처리 불가**: 단일 세션에서 독립적 서브태스크를 동시에 처리하기 어려움

## 결정 (Decision)

**B+A 하이브리드** 방식을 채택한다:

- **터미널 1 — 관리자** (`claude --model claude-sonnet-4-6`): 설계, 작업 분해, 코드 검수, 커밋 제안
- **터미널 2 — 실행자** (`claude --model claude-haiku-4-5-20251001`): 지시서 수신 → 서브에이전트 분배 → 결과 취합

두 세션은 **파일 기반 채널**로 통신한다:

```
docs/work-logs/TASK.md    ← 관리자가 작성하는 작업 지시서
docs/work-logs/RESULT.md  ← 실행자가 작성하는 결과 보고서
```

실행자는 **패턴 1** (탐색 → 병렬 구현 → 검증)을 기본으로 서브에이전트를 분배한다:

```
Phase 1: Agent-탐색A + Agent-탐색B  (직렬)
Phase 2: Agent-구현A + Agent-구현B  (병렬, 독립 파일)
Phase 3: Agent-검증                  (직렬, ruff + mypy + pytest)
```

### 비교 검토한 선택지

| 방식 | 설명 | 탈락 이유 |
|------|------|-----------|
| **A안** (단일 세션 + Agent) | Sonnet 단일 세션에서 Agent 도구로 탐색 위임 | 모델 비용 최적화 없음, 컨텍스트 분리 효과 제한적 |
| **B안** (멀티 터미널만) | 두 터미널이 각자 독립 작업 | 실행자 내 병렬 처리 없음, 탐색-구현-검증 직렬 |
| **B+A 하이브리드** (채택) | 멀티 터미널 + 실행자 서브에이전트 | 위 두 방식의 장점 결합 |

## 결과 (Consequences)

### 이점 (Benefits)

- **비용 최적화**: 설계(Sonnet) / 반복 구현(Haiku) 역할 분리
- **컨텍스트 보존**: 관리자 세션은 설계 맥락만 유지, 구현 디테일 불필요
- **병렬 처리**: 독립적인 서브태스크(구현A + 구현B)를 동시에 처리 가능
- **작업 이력**: TASK.md / RESULT.md가 작업 로그로 남음
- **책임 분리**: 탐색 → 구현 → 검증 단계가 명확히 분리됨

### 단점 (Drawbacks)

- **초기 설정 비용**: TASK.md 작성에 관리자 시간 필요
- **파일 채널 한계**: 두 세션 간 실시간 소통 불가 (비동기)
- **조율 품질 의존**: Haiku의 서브에이전트 분배 품질이 TASK.md 상세도에 의존

### 리스크 (Risks)

- **파일 충돌**: 두 터미널이 같은 파일을 동시에 수정할 경우 충돌 가능
  - 대응: 관리자가 TASK.md에 **담당 파일을 명시**, 실행자는 지정된 파일만 수정
- **서브에이전트 토큰 폭발**: 서브에이전트 수가 많아지면 비용 선형 증가
  - 대응: 서브에이전트 수 최대 4~5개 제한, Agent당 단일 책임 원칙
- **Haiku 판단 오류**: 복잡한 조율을 Haiku가 잘못 판단할 수 있음
  - 대응: TASK.md에 단계별 지시를 구체적으로 작성 (Haiku 자율 판단 최소화)

## 부록 (Appendix)

### Haiku 활용 기준

```
Sonnet/Opus 써야 할 때:        Haiku 써도 되는 때:
  - 아키텍처 결정                 - 설계가 완료된 코드 구현
  - 코드 검수 (버그 탐지)         - 반복 코드 (테스트, 보일러플레이트)
  - 복잡한 알고리즘 설계          - 린트/포맷 수정
  - ADR 작성                      - 문서 갱신
```

### TASK.md 표준 구조

```markdown
## 작업 ID / 제목 / 배경
## 실행 순서 (패턴 1)
  Phase 1: 탐색 (직렬) — 결과를 RESULT.md에 기록
  Phase 2: 구현 (병렬) — 독립 파일 각자 담당
  Phase 3: 검증 (직렬) — ruff + mypy + pytest
## 완료 기준 (체크리스트)
```
