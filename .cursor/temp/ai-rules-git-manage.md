시니어 개발자의 관점에서 이 문제는 '개인의 취향'과 '팀의 컨벤션' 사이의 경계를 정하는 아주 중요한 설계 포인트입니다. 결론부터 말씀드리면, "핵심 룰(Core Rule)은 공유하고, 개인의 도구 설정(Personal Preference)은 분리한다"가 정답입니다.
프로젝트의 형상관리(Git)에 AI 컨텍스트를 포함할 때의 가이드라인을 정리해 드립니다.
1. Git에 포함해야 할 것: "프로젝트의 헌법"
팀원 누구(혹은 어떤 AI 에이전트)가 투입되어도 프로젝트의 정체성을 유지하기 위한 정보는 반드시 공유되어야 합니다.

* CLAUDE.md 또는 .cursorrules: 이 파일들은 단순한 메모리가 아니라, 이 프로젝트의 '코딩 표준'이자 '아키텍처 설계도'입니다.
* 예: "우리 프로젝트는 테일윈드를 쓰고, 비동기 처리는 반드시 이 라이브러리를 써야 해"라는 규칙은 모든 AI가 알아야 하므로 Git으로 관리합니다.
* Prompt Templates: 반복적으로 사용하는 복잡한 프롬프트(예: PR 생성용, 유닛 테스트 작성용)는 코드의 일부로 취급하여 공유하는 것이 생산성 측면에서 압도적으로 유리합니다.

2. Git에서 제외해야 할 것: "개인의 운전 습관"
다른 개발자의 작업 환경을 침범하지 않기 위해 .gitignore에 넣어야 할 것들입니다.

* AI 세션 로그/캐시: 에이전트가 작업하며 남긴 임시 로그나 개인적인 대화 기록.
* 개인별 API 키 및 로컬 환경 설정: .env 파일과 마찬가지로 보안 및 개인화된 영역입니다.
* 사용자별 커스텀 인스트럭션: "나는 설명을 짧게 듣는 걸 좋아해" 같은 개인 성향은 프로젝트 공통 룰에 포함되면 타인에게 방해가 됩니다.

3. '침범'하지 않고 공존하는 전략 (Best Practice)
시니어들이 추천하는 레이어드(Layered) 세팅 방식입니다.

   1. Shared Layer (Git 관리): CLAUDE.md에 프로젝트 공통 규칙(기술 스택, 폴더 구조, 네이밍 규칙)을 명시합니다. 이는 '침범'이 아니라 '가이드라인 제시'입니다.
   2. Personal Layer (Local 관리): 클로드 코드나 커서의 개인 설정(Settings) 기능을 활용합니다. 프로젝트 루트가 아닌, 내 컴퓨터의 전역 설정에 본인의 취향을 담습니다.
   3. Override Layer: 만약 특정 팀원이 다른 방식의 AI 보조를 원한다면, 공통 룰을 기반으로 하되 본인의 로컬에서만 유효한 추가 지침 파일을 만들어 사용하게 합니다.

4. 시니어의 조언: "AI 컨텍스트는 이제 문서(Documentation)의 진화형입니다"
예전에는 README.md를 잘 쓰는 게 실력이었다면, 이제는 AI가 읽고 즉시 실행할 수 있는 CLAUDE.md를 잘 구성하는 게 실력입니다. 이것을 공유하는 것은 다른 사람의 영역을 침범하는 것이 아니라, "우리 팀의 AI 비서를 똑똑하게 만드는 공유 지식 베이스"를 구축하는 아주 세련된 행위입니다.
